4 Error Handling🔗

This chapter describes the error-handling mechanisms that the library provides, when to use each, and how to build your own.

The library has no Maybe or Either values. Errors are either effects (resolved by a handler), a #f result (resolved by catch), or ordinary Racket exceptions raised by impure code.

4.1 Available Mechanisms🔗

4.1.1 The failure effect🔗

 (require freer-lib/effects/failure-effect)
  package: freer-lib

struct

(struct failure-effect (msg)
    #:extra-constructor-name make-failure-effect)
  msg : any/c
An effect descriptor that carries a failure message.

procedure

(failure msg) → free?

  msg : string?
Describes a failure with the message msg by performing a failure-effect.

There is no default handler. The handler that you pass to run decides what a failure means: raise an error, stop with a value, or recover.

Examples:
> (define (safe-div a b)
    (if (zero? b)
        (failure "division by zero")
        (return (/ a b))))
> (run (safe-div 6 3)
       (lambda (eff k)
         (match eff
           [(failure-effect msg) (return (list 'failed msg))])))

2

> (run (safe-div 1 0)
       (lambda (eff k)
         (match eff
           [(failure-effect msg) (return (list 'failed msg))])))

'(failed "division by zero")

Because the handler does not call k, the rest of the computation is skipped.

4.1.2 The abort effect🔗

Module freer-lib/effects/abort-effect (documented under Standard Effects). (abort) describes an immediate stop, with no message, by performing an abort-effect. A handler that does not call k ends the computation.

Examples:
> (require freer-lib/effects/abort-effect)
> (define (check-positive x)
    (do-m [_ <- (if (negative? x) (abort) (return (void)))]
          (return x)))
> (run (check-positive -1)
       (lambda (eff k)
         (match eff
           [(abort-effect) (return 'stopped)])))

'stopped

4.1.3 try and catch🔗

Module freer-lib/try-catch (documented under Standard Effects). try treats a #f result as a failure. When the computation returns #f, try signals an internal failure that carries the fallback computation. catch intercepts that failure, discards the rest of the enclosed computation, and runs the fallback instead.

Example:
> (run (catch
         (do-m [a <- (return 1)]
               [b <- (try (return #f) (return 'fallback))]
               (return (list a b))))
       (lambda (eff k) (k eff)))

'fallback

catch only intercepts failures raised by try. It does not intercept the failure effect, which must be handled by the handler given to run.

4.1.4 Exceptions🔗

The impure handlers (file system, commands, HTTP, logging) catch exn:fail? exceptions from the outside world and re-raise them with error. They reach the caller of run as exn:fail. To recover, wrap the call to run in with-handlers.

Pure code must not raise: a failure that can occur with valid input is a value or an effect.

4.2 Choosing a Mechanism🔗

Situation

  

Use

A reportable error that a caller may handle

  

failure

An early exit with no payload

  

abort

A single computation that returns #f on failure

  

try and catch

A failure of the outside world inside an impure handler

  

an exception

  • Prefer failure when the cause matters, since it carries a message and each run can handle it differently, for example in tests.

  • Prefer abort when the only information is that the computation stopped.

  • Use try and catch when you need a local fallback and the failure is naturally #f. A legitimate #f result is indistinguishable from a failure.

  • Raise exceptions only in impure code, such as a handler.

4.3 Creating a Custom Mechanism🔗

Create your own when the existing ones cannot carry the information you need, for example a structured error with a code, or a recovery policy that is specific to your domain.

There is no macro for defining effects. A mechanism has three parts:

  • a struct that describes the failure,

  • a constructor that calls perform on an instance of the struct,

  • an interpreter, used as (or inside) the handler for run, that matches the struct and returns a value without calling k.

Examples:
> (struct reject-effect (code))
> (define (reject code)
    (perform (reject-effect code)))
> (define (validate-age age)
    (cond [(not (integer? age)) (reject 'not-a-number)]
          [(negative? age) (reject 'negative)]
          [else (return age)]))
> (define (handle-reject eff k)
    (match eff
      [(reject-effect code) (return (list 'rejected code))]))
> (run (validate-age 30) handle-reject)

30

> (run (validate-age -5) handle-reject)

'(rejected negative)

To recover inside a larger computation instead of ending the whole run, write an interpreter that walks the computation, as catch does. It matches the computation: a pure value is returned, your effect yields the fallback, and any other effect is forwarded by performing it again and continuing with the interpreter on the rest.

Examples:
> (define (recover-reject computation fallback)
    (match computation
      [(pure v) (return v)]
      [(impure (reject-effect _) _ _) (return fallback)]
      [(impure eff k _)
       (>>= (perform eff) (lambda (v) (recover-reject (k v) fallback)))]))
> (run (recover-reject
         (do-m [x <- (return 1)]
               [y <- (reject 'boom)]
               (return (+ x y)))
         'recovered)
       (lambda (eff k) (k eff)))

'recovered
